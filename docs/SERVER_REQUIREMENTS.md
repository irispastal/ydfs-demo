# Windows 应用兼容性：服务端能力需求

更新：2026-11-16。本文是根据当前客户端实现及 Windows 文件操作语义提出的服务端契约，不表示现有移动云盘已经提供这些能力，也不表示本次 FUSE 3 升级实现了它们。

## 1. 结论与职责

FUSE 3 解决 Linux 挂载接口的升级。资源管理器、Office、文件锁和打开后删除，还依赖 Windows 驱动/适配层正确处理共享模式、打开句柄、缓存与错误，以及服务端提供并发安全的文件和目录操作。

单个挂载实例内，驱动和客户端可以协调本地句柄与锁；一旦多台电脑、网页端或其他应用同时访问，就必须由服务端统一执行冲突检查。只在本地加锁或隐藏临时文件，无法阻止其他入口覆盖数据。

| 场景 | 客户端/驱动负责 | 服务端需要提供 |
| --- | --- | --- |
| 资源管理器复制、重名和刷新 | 属性、容量、错误映射、缓存失效、创建/覆盖模式 | 原子创建且重名失败；稳定 fileId；准确元数据；分页一致性；变更游标 |
| Office 临时文件保存与替换 | 支持临时文件、截断、flush/fsync、属性操作；失败保留待上传内容 | 新内容暂存后完整提交；版本条件检查；原子替换；请求幂等与结果查询 |
| 文件锁与共享打开 | 本机的共享模式及字节范围锁由 Windows/WinFsp 协调；适配层负责需要上云的协调 | 跨客户端的打开租约、共享模式冲突检查、字节范围锁或明确的独占写契约；失效租约的写入拒绝 |
| 覆盖改名、跨目录移动 | 正确区分普通替换、禁止覆盖、交换和 Windows ReplaceFile | 在同一事务中更新源/目标目录项；检查源/目标版本；保留仍被句柄引用的旧对象 |
| 删除正在打开的文件 | 检查 FILE_SHARE_DELETE；区分 delete-pending 与 POSIX unlink；保持句柄有效 | 名称与对象生命周期分离；按对象/版本继续读取；租约结束后回收；关闭不能复活名称 |

依据：[CreateFileW 共享模式](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)、[LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)、[DeleteFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew)、[ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)、[WinFsp 原生接口](https://winfsp.dev/doc/WinFsp-API-winfsp.h/)。

## 2. 第一优先级：防止保存失败和丢数据

### 2.1 稳定身份与版本读取

- `fileId` 在改名、跨目录移动、内容更新期间保持稳定，不能用路径充当对象身份。
- 内容版本 `revisionId` 不可变；目录位置、名称、属性还需要元数据版本或统一的对象版本。仅有内容摘要不足以发现改名冲突。
- 下载取址接受 `fileId + revisionId`，URL 过期后能对同一版本续签。旧句柄的分块读取不能前半段来自旧版本、后半段来自新版本。
- 对已删除或被替换的对象，持有有效读取租约的句柄仍能读取指定版本；回收站保存对象不等于保证这种读取契约。

### 2.2 原子创建、内容提交与条件更新

- 创建支持 `createNew`：同一父目录下，按服务端统一的名称比较规则检查唯一性并创建，必须是一个原子操作。并发创建同名文件只能一个成功，包含 0 字节文件。
- 上传会话与可见版本分离。分片尚未完成时，其他客户端看到旧完整版本；完成校验和提交后才看到新完整版本。临时文件可以先以独立名称创建，不能因此提前截断原文件。
- 修改已有内容时，提交携带 `expectedRevision`（CAS，即比较版本后再更新）。服务端在实际提交时再次检查，而非仅在开始上传时检查；版本变化返回冲突，保留旧内容和可恢复的上传会话。
- 如果操作涉及名称、位置或属性，也必须检查相应版本；不能把内容 CAS 当作目录事务。
- 提交成功的持久化保证必须明确：何时内容可读、何时目录可见、何时达到约定的持久化级别。客户端只有等服务端确认后，才可按这一契约完成 fsync。

### 2.3 原子改名与替换

提供单个服务端事务，完成“检查源/目标 → 移动并改名 → 替换目标 → 发布目录变化”。同一个挂载卷内的跨目录操作也需要这个保证。不能依靠“先删除目标，再移动，再改名”来模拟。

事务至少携带：源对象 ID、源版本、目标父目录 ID、目标名称、期望目标状态（不存在，或指定 ID/版本）、替换模式、幂等请求 ID。目标状态变化应返回冲突，不能删除刚被另一个客户端更新的文件。

模式需区分：

- 普通 rename/replace：目标名称变为源对象，已打开的旧目标句柄仍引用旧对象；适配层必须维护这种身份关系。
- 禁止覆盖：检查目标不存在和移动同时发生，不能先 list 再 move。
- Windows ReplaceFile：通常还要求保留目标文件的身份及指定元数据。可另提供“按目标 fileId 原子发布暂存内容”的接口，由 Windows 适配层映射，不能与 POSIX rename 混为一谈。
- 交换、带备份的替换：若声明支持，两个名称或备份的变更也需同一事务；未实现时明确返回不支持。

失败与超时的处理也必须明确：事务拒绝时无部分变更；响应丢失时能按请求 ID 查询最终结果。原子性保证每一步事务，不自动把 Office 发出的多次独立调用变成一个大事务。

### 2.4 幂等、恢复及明确错误

- 对创建、完成上传、改名、删除提供持久化的幂等键。相同键与相同参数重试返回原结果；相同键但参数不同返回错误。需定义键的有效期。
- 提供操作状态查询，区分处理中、已提交、失败，解决“客户端超时但服务端已成功”。跟踪请求的 tid 只有在服务端提供这种保证时才是幂等键。
- 错误应可机器判断：不存在、已存在、目录非空、版本冲突、共享冲突、锁冲突、租约失效、权限不足、配额不足、不支持。客户端再映射为 errno/NTSTATUS。
- 提供过期上传会话回收与状态查询，允许失败续传或安全重试。

## 3. 严格的多端语义：打开租约、锁及删除

### 3.1 共享打开与字节范围锁是两种能力

Windows 的共享打开限制整份文件后续能否被读、写、删除/改名；字节范围锁限制特定区间的访问。Office 使用的 `~$...` 等锁文件也不等于操作系统的锁。

如果只要求同一台电脑、同一挂载实例内的锁，不需要服务端逐次接收 LockFileEx；应先验证 Windows/WinFsp 的本地处理。若要求多台电脑之间保持同等约束，服务端需要：

- `open` 原子检查并注册 `desiredAccess + shareMode`，返回 openToken、对象/版本与租约期限。新访问权限必须被既有共享模式允许，既有访问权限也必须被新共享模式允许。
- `renew/close` 和断线回收。租约过期后客户端须停止写入或重新申请，不能继续使用旧缓存提交。
- 单调增加的 fencing token（隔离旧租约的令牌），在内容提交、替换、删除等实际执行点验证。仅有 TTL 锁无法阻止失联旧客户端晚到的写入。
- 如果承诺跨端字节范围锁，锁需绑定句柄所有者、区间、共享/独占模式，支持释放、等待/立即失败、异常回收，并在冲突的读取/写入路径实施约束。当前整文件提交接口不能简单照搬区间写，需定义兼容策略或使用独占写租约。
- 网页端、同步客户端等所有写入口必须执行同样的检查；否则只能称为参与客户端之间的协作锁。

若服务端只能提供 CAS，可做到检测并发覆盖并保留冲突副本，但不能声称支持跨端 Windows 文件锁。

### 3.2 打开后删除与替换旧目标

需要把目录项生命周期与内容对象生命周期分开：移除名称不意味着立即清除被句柄引用的内容。

- Windows 普通 DeleteFile 先遵守共享删除权限与 delete-pending 规则；POSIX unlink 可立即移除名称。具体名称何时允许重用由所选择的语义决定，不能全都按 POSIX unlink 处理。
- 服务端支持“移除目录项/标记待删除”与“最终回收”分离。有效打开租约保住对象及所需版本；已有句柄按令牌继续访问，新打开按目录状态拒绝。
- 已删除对象上的写入只能作用于该对象的存活上下文，或按契约拒绝；不能通过普通上传重新创建同名文件，也不能覆盖后来创建的同名新对象。
- 最后一个有效租约关闭或过期后允许异步回收；同时遵守回收站/历史版本保留政策。租约过期后的重新打开不能自动获得对旧对象的权限。
- 替换目标时，对旧目标句柄也应用同一套存活与回收规则。

## 4. 元数据、目录一致性和性能

- 服务端统一定义名称规范、大小写比较、Unicode 处理、长度限制及仅改变大小写的改名。原子唯一性检查必须使用相同规则；客户端的 Python casefold 不能直接当作 NTFS 完整规则。
- 支持保存创建/修改时间、只读/隐藏等属性；按产品需求提供 ACL、扩展属性或 ADS，并明确不支持项。不能长期把设置属性的请求全部返回成功而不保存。
- 提供按 ID 查询和批量属性查询；目录游标应对应稳定快照或可检测的目录版本，避免翻页时漏项/重复。
- 写入/改名/删除成功后提供读己之写的保证；目录变更具有递增序号，可通过变更流或增量轮询获得。游标失效或事件断档时可全量重建缓存。
- 变更事件需覆盖外部客户端，且在事务提交后发布。只有缩短 TTL 无法保证多端即时一致。
- Range 读取仍足够支持下载；随机写、增量块提交、服务端复制等主要改善大文件性能，并非单独解决 Office 保存正确性的前提。

## 5. 建议的接口契约草案

以下是供服务端评审的逻辑操作名，不是当前 SaaS 已存在的 HTTP 接口。可用现有协议扩展或单独网关实现，但网关必须能控制所有并发入口，才能提供全局保证。

| 逻辑操作 | 主要参数 | 核心保证 |
| --- | --- | --- |
| createNew | parentId, name, type, requestId | 原子唯一性、空文件、幂等 |
| beginUpload / commitContent | fileId, expectedRevision, uploadId, hash, leaseToken, requestId | 暂存不污染旧版本；提交时 CAS；持久化结果 |
| rename | sourceId, expectedSourceVersion, targetParentId, targetName, expectedTarget, mode, requestId | 名称/位置/替换在同一事务提交 |
| replaceContents | targetId, expectedTargetVersion, stagedRevision, metadataPolicy, requestId | 按约定保留目标身份并发布完整内容 |
| open / renew / close | fileId, desiredAccess, shareMode, openToken | 跨端共享检查、租约和 fencing |
| lockRange / unlockRange | openToken, offset, length, mode, waitPolicy | 跨端区间冲突检查，受约束的访问必须执行锁检查 |
| unlink / finalizeDelete | fileId, expectedVersion, openToken, deleteMode, requestId | 目录项与对象分离，最后租约后回收 |
| downloadRevision | fileId, revisionId, openToken | 版本固定、URL 可续签、保留期内 Range 可读 |
| getOperation / changes | requestId 或 changeCursor | 超时结果可确认；缓存变更可追踪 |

先实现原子创建、CAS 内容提交、原子改名/替换、幂等查询和稳定版本读取；如果目标包含跨端锁和打开后删除，再把打开租约与对象存活管理作为必需能力一起设计。不要先承诺全量桌面文件系统语义，再把这些能力当作后续优化。

## 6. 当前 Demo 的具体缺口与验收

代码中的已知限制：

- `core/fs.py:rename` 先回收目标，再执行 move 与 rename。服务端任一步失败都可能留下中间状态；本地 RLock 不能使这组远程调用成为事务。
- `core/api/client.py:upload` 没有传期望版本；`fileId` 和新 `revisionId` 不足以证明具有 CAS。创建冲突时核心层还可能转为覆盖，需要在产品化时改为显式冲突策略。
- Reader 虽按 revision 建本地缓存键，但取下载 URL 只传 fileId，尚未锁定远端版本。
- 删除前会把本挂载中打开的对象整份下载暂存，以维持本地句柄读取。大文件有延迟与空间代价，且不能保护另一台电脑的句柄。
- 暂存使用临时文件；release 失败后仍会关闭最后的暂存句柄。产品化需要持久化失败队列及恢复入口，服务端提供恢复接口也不会自动补上客户端的数据保留。
- chmod/chown/utimens 当前直接返回成功；没有跨端打开租约或锁协议。两端 FUSE 3 不支持的 rename 标志均明确拒绝。本机 Windows 共享模式/字节范围锁、ReplaceFileW、打开后删除已通过自动测试，但这些不提供跨客户端保证。

现有客户端没有使用上述服务端能力，不代表远端服务一定没有，需要向服务端确认正式契约并联调。

建议验收必须覆盖：

1. 两客户端并发 createNew，同名仅一个成功；CAS 提交同一旧版本，仅一个成功，另一方保留待提交数据。
2. 覆盖改名在提交前后注入失败：其他客户端只看到事务前或事务后的目录状态，目标不因部分失败丢失；响应丢失后按请求 ID 查得同一结果。
3. 打开旧目标后替换：新打开看到新对象，旧句柄仍按约定读取旧对象；分块读期间新版本发布且 URL 过期，旧句柄仍读同一版本。
4. 无 FILE_SHARE_DELETE 的打开阻止删除；允许共享删除时按 delete-pending/POSIX 模式分别验证。关闭旧句柄不能删除或覆盖同名新对象。
5. 两台电脑测试共享模式、区间锁及互相冲突；租约失效的客户端尝试晚到提交，服务端拒绝。网页端也不能绕过。
6. Windows 资源管理器复制/覆盖/取消、Word/Excel 打开/编辑/保存/另存为/异常退出，以及网络中断/配额不足后的恢复。Office 实测是独立验收，不能由 Python 文件操作通过来替代。
