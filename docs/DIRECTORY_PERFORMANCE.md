# 目录打开性能分析与优化

测量日期：2026-11-16。结论：本次复现的主要瓶颈是属性查询重复扫描同级目录，其次是串行分页请求过多。完成名称索引和分页优化后，3000 项目录在 Windows 实际挂载下首次枚举的中位耗时从 **2910 ms 降到 316 ms（减少 89.1%）**，再次枚举从 **2235 ms 降到 154 ms（减少 93.1%）**。

后续已使用当前 Y: 的真实云盘配置完成只读复测和资源管理器验证，见 [真实云盘目录复测](REAL_CLOUD_DIRECTORY_PERFORMANCE.md)。真实目录样本较小，冷打开主要受网络和全局锁影响，不能套用本页大目录 mock 的加速比例。

## 测试口径

- Windows、x64 Python 3.14.3、WinFsp FUSE 3.2 绑定，使用独立 X: 盘；不重启或改动已有 Y: 挂载。
- 本机 HTTP mock，每次 `/file/list` 注入 15 ms 延迟；目录含 100、1000、3000 个文件，另有一个父目录节点。真实走 HTTP 客户端、缓存、Filesystem、FUSE 适配器；实际挂载再经过 WinFsp 和 Win32 文件系统调用。
- 核心测试每组 5 次，冷列目录前清空相关缓存，再逐项取属性，最后热列目录；属性查询使用大小写变体，覆盖 Windows 回退匹配。测试断言文件数、名称唯一性、大小，并确认热操作没有新增 HTTP 请求。
- 挂载测试每组独立重挂载 3 次，每次执行两遍 `os.scandir + entry.stat`，分别记为冷、热枚举。只统计枚举阶段，不含挂载启动时间。文件名和大小逐项验证，测试结束卸载专用盘。
- 前后均启用相同 INFO 诊断日志、60 秒缓存 TTL，避免基线执行期间过期。产品默认 TTL 仍为 5 秒。
- 初始未优化代码已直接测出卡顿：3000 项的实际冷/热枚举分别约 3033/3524 ms。为增加重挂载样本，在 `.local/perf/baseline-source` 中还原相同旧扫描算法、100 项分页，保留相同适配器和日志代码，得到下文基线；未回滚工作区及其已有改动。
- 本页数据是首轮受控 mock 和 Win32 枚举结果，**不是资源管理器窗口首帧或缩略图加载时间，也不代表真实云端延迟**。项目根的 `ydfs.local.json` 指向本机 mock；后续从现有 Y: 进程确认真实配置另存于其他位置，真实复测结果单独记录，未在真实云端写入或删除文件。

## 分阶段定位

用 `time.perf_counter` 记录耗时，统一前缀 `[directory-perf]`。`pid + trace` 关联一次调用及各分页；`target` 是路径或目录 ID 的 SHA-256 前 12 位，便于关联同一目标，不输出原始名称。

| 阶段 | 字段 | 用途 |
| --- | --- | --- |
| 锁等待 | `lock_wait` | 区分排队与实际处理 |
| 路径解析、名称匹配 | `lookup`, `name_lookup` | 确认是否重复扫描目录 |
| 缓存填充、索引构建 | `cache_fetch`, `cache_index` | 识别冷缓存开销 |
| HTTP 等待、JSON 解析 | `http_wait`, `json_decode` | 区分网络与解码成本 |
| 本地覆盖、列表合并 | `local_overlay`, `merge_children` | 跟踪未提交文件叠加 |
| 属性转换、生成名称 | `attributes`, `names` | 跟踪适配层处理 |
| WinFsp 填充 | `native_fill` | 跟踪原生 filler 回调 |

`counts` 包含缓存命中/未命中、路径层数、分页数、返回项数和填充项数。`list_page` 另记每页耗时、项数和是否继续翻页。`status=error` 保留失败操作耗时，不打印异常中的敏感正文。INFO 记录列目录、分页及不少于 50 ms 的属性查询；DEBUG 额外记录每个属性查询。文件日志支持轮转。

**各阶段为包含子阶段的耗时，不能相加。** `total_ms` 才是本次回调总耗时。目录枚举后操作系统还可能逐项调用 `getattr`，因此仅看 `readdir.total_ms` 不能代表整个窗口打开时间，需要同时观察属性查询。DEBUG 会增加日志写入开销，性能对比统一使用 INFO；DEBUG 只用于阶段归因。

验证的假设与证据：

1. **重复扫描是主因。** 原来的 `lookup` 每经过一层路径都调用 `children`，复制和过滤整个列表，再线性找名称；Windows 大小写回退会再扫描一次。枚举 N 项后逐项查询属性，累计接近 O(N²)。回归测试对 1000 项缓存做一次属性查询，原版本触发 1000 次名称 key 计算，限制为不超过 4 次时失败；优化后通过。
2. **100 项分页放大冷打开耗时。** 3000 项目录需 30 页，加父目录共 31 次请求。目录遍历遵循 `nextPageCursor`，原流程虽正确，但串行网络等待较多。
3. **原生填充不是当前主因。** 3000 项原生冷列目录的 `native_fill` 中位耗时约 6.24 ms，优化后约 4.57 ms；相比之下 HTTP 等待从约 649 ms 降到 98 ms。基线曾出现约 633 ms 的属性查询锁等待，与另一线程分页拉取重叠，说明慢请求会放大排队。

DEBUG 的单次 3000 项属性遍历中，`lookup` 累计从 2769 ms 降到 45 ms；旧版其中约 1551 ms 在合并同级列表、1153 ms 在线性匹配名称。新版属性查询不再构建同级列表。它是归因样本，不能与下方 INFO 测量直接混算。

## 优化方案与实现

1. **按目录建立名称索引。** 一次拉取完成后同时构建精确名称索引与 Windows casefold 索引。单个缓存内节点查找由 O(N) 变为平均 O(1)，整批属性查询接近 O(N × 路径层数)。精确名称优先，忽略大小写回退仍按服务端原有顺序取首个匹配项。
2. **保留本地覆盖一致性。** 属性查询先检查未提交的本地文件，再查云端缓存；大小仍取暂存文件。列目录仍合并本地覆盖。创建、提交、改名、移动和删除沿用父目录失效机制，列表与索引一起刷新，未额外延长负查询缓存寿命。过期、零 TTL、刷新失败均已覆盖。
3. **减少分页往返。** 默认 `page_size` 从 100 调到协议允许的 1000，并增加命令行/JSON 配置和范围校验。仍逐页跟随游标，空页但有游标会继续，重复游标会失败，不并行猜测游标。E2E 验证显式用 100 项分页，使原来的 250 项测试继续覆盖三页；默认 1000 项分页由性能测试覆盖。
   提交前补测还复现了并发上传导致的分页边界移动：250 个唯一文件被枚举为 253–254 项。分页汇总现按稳定 `fileId` 去重，重复项计入 `duplicate_items`，重叠页仍继续跟随游标；该修复避免重复名称，不声称提供服务端快照一致性。新增重叠页回归测试在修复前失败。
4. **减少不必要列表处理。** 没有本地覆盖时，列目录不再逐项 casefold 过滤；保留返回列表副本。
5. **保留可用的性能日志与测试工具。** 未引入路径永久缓存，未调整文件读写、改名或删除的锁语义。

索引增加 O(N) 内存，保存节点引用而不复制节点正文；已有目录缓存仍按 TTL 刷新。全局锁仍会在网络操作期间持有，以保持现有一致性。此次通过减少扫描和请求数缩短持锁时间；后台大文件传输下的锁竞争尚未专门压测。如果后续日志显示 `lock_wait` 仍主导，应另行设计按目录/文件的锁，并验证并发失效和写入语义。

## 前后对比

核心阶段：5 次中位数，毫秒；请求数包含父目录。

| 项数 | 冷列目录 前→后 | 全部子项属性 前→后 | 两阶段总计 前→后 | 总计减少 | 请求 前→后 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 34.89 → 34.97 | 5.95 → 2.30 | 41.22 → 37.24 | 9.7% | 2 → 2 |
| 1000 | 196.27 → 39.34 | 349.93 → 25.67 | 565.33 → 64.35 | 88.6% | 11 → 2 |
| 3000 | 578.97 → 81.67 | 3502.01 → 76.13 | 4080.98 → 158.01 | 96.1% | 31 → 4 |

“两阶段总计”对每次样本先求和再取中位数，不一定等于两列中位数之和。100 项的冷列目录基本没有变化，符合分页数未变的预期。

实际 WinFsp 挂载：3 次重挂载的中位数，毫秒。

| 项数 | 冷枚举 前→后 | 减少 | 热枚举 前→后 | 减少 |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 50.62 → 45.08 | 11.0% | 8.80 → 5.31 | 39.6% |
| 1000 | 580.12 → 91.45 | 84.2% | 274.17 → 54.24 | 80.2% |
| 3000 | 2910.06 → 315.89 | 89.1% | 2234.98 → 153.67 | 93.1% |

有明显的系统抖动：优化后 3000 项冷枚举三个样本为 315.886、1119.391、254.985 ms；基线为 2738.478、3311.196、2910.057 ms。样本量较小，不据此推断 P95/P99。CPU 大量扫描与 HTTP 请求数的下降更稳定。

单独验证名称索引（3000 项，仍强制每页 100 项）：核心冷列目录 552.34 ms、属性查询 70.50 ms、总计 625.27 ms，仍请求 31 次；实际冷/热枚举 834.64/136.28 ms。说明索引解决了热目录的主要 CPU 开销；进一步增大分页主要改善冷打开，而不是依靠延长 TTL 获得收益。

## 复测与回归

在项目根目录运行，Windows 的 X: 必须空闲；不带 `--mount` 可以只测核心链路。

```powershell
.\.venv\Scripts\python.exe test/perf/directory_open.py --output .local/perf/current.json --repeats 5 --mount X: --mount-repeats 3
.\.venv\Scripts\python.exe test/perf/directory_open.py --entries 3000 --page-size 100 --output .local/perf/index-only.json
.\.venv\Scripts\python.exe test/perf/directory_open.py --entries 3000 --repeats 1 --log-level DEBUG --output .local/perf/detail.json
.\.venv\Scripts\python.exe -m unittest discover -s test -v
```

实际启动时可用 `python -m cmd.ydfs --config ydfs.local.json --log-file .local/ydfs.log --log-level DEBUG` 捕获反馈目录的属性阶段；日常改回 INFO。日志字段和 JSON 配置方法见 README。已有挂载须重启才会加载新代码。
