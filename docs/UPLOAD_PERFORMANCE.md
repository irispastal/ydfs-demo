# 大文件上传启动优化

## 原因与实现

原来 `Client.upload` 在 `/file/create` 之前从头读取暂存文件并计算完整 SHA-256/SHA-1。文件写入本地后还要再扫描一遍,这段时间没有上传请求。重试提交和重名冲突重试也会重复扫描。

现在 `core/io/staging.py` 的 `StagedFile` 维护一个已摘要且内容未变的连续前缀:

- 顺序写入和追加直接使用成功写入的内存字节更新摘要,不额外读取文件。状态大小固定,不缓存文件内容。
- 预分配不影响后续从零开始的顺序摘要。读文件、查询属性和 seek 不改变摘要。
- 覆盖已摘要区域或截断到该区域以内时重置摘要;提交时只扫描尚未摘要的部分。稀疏写入的空洞、扩展后的零填充也参与完整摘要。
- 下载旧内容到暂存时累积摘要;后续纯追加可复用旧内容的摘要前缀。
- 上传完成、上传失败和重名重试都保留当前摘要;内容变更通过同一个暂存对象使摘要失效。同一文件的多个句柄共享摘要,上传期间同文件变更等待条件变量,不同文件继续操作。
- `Client.upload` 对普通文件流仍执行完整扫描,支持原有直接上传调用;分片数量超限在扫描前返回错误。

`/file/create` 与 `/file/complete` 仍发送同一份完整文件摘要,服务端校验和秒传行为不变。没有用分片摘要拼接代替 SHA-256。

## 本地测量

2026-11-16,Windows x64 / Python 3.14.3。文件 256 MiB,每次写入 64 KiB,三次交替运行取各项中位数:

| 指标 | 原完整扫描路径 | 增量摘要路径 |
| --- | ---: | ---: |
| 本地写入耗时 | 133.573 ms | 678.758 ms |
| 写完到首次 `/file/create` | 607.720 ms | 0.556 ms |
| 开始写入到首次 `/file/create` | 741.293 ms | 679.314 ms |
| 上传准备阶段 read 调用数 | 257 | 0 |

写完后的准备等待基本消除;包含写入和摘要计算的总耗时约减少 8.4%。计算成本转移到了写入回调,并未消失。该基准不包含挂载驱动、真实网络或云端提交时间,不能作为上传带宽指标。

复现命令(项目根目录):

```powershell
.venv/Scripts/python.exe test/perf/upload_start.py --size-mib 256 --chunk-kib 64 --runs 3
.venv/Scripts/python.exe -m unittest discover -s test -v
```

基准运行实际 `Filesystem.write → flush → Client.upload` 路径,基线仅将暂存对象替换回原始 `TemporaryFile`;两组均在 `/file/create` 处校验完整摘要并返回模拟秒传响应,不访问网络和真实账号。脚本同时输出每次样本、写入时间、准备时间与总时间,避免将计算前移误报为整体数百倍加速。

## 验证与限制

新增回归测试固定断言顺序拷贝的上传准备阶段零读取,并覆盖预分配、上传失败后复用、追加、算法切换、空文件、零截断及两种算法下的随机写入/扩展/截断。另使用真实 HTTP 客户端和本地模拟服务验证多分片提交、重新打开后追加、覆盖和截断,由服务端重算摘要并检查最终内容。完整单元测试共 27 项通过。

随机覆盖已摘要的内容仍可能需要重新扫描全文件。所有路径仍先暂存,再同步提交;如需在文件尚未写完时开始网络上传,需要另行调整上传协议与生命周期,确认服务端是否允许推迟提供整文件摘要。当前改动无需服务端变更。

## 上传阶段日志与锁范围

针对 `gateway-sparse.vmdk` 在复制 99% 时等待的问题,旧日志只显示两次属性查询各等全局锁约 9.4 秒,没有上传阶段记录。上传现在使用 `[upload-perf]` JSON 日志,同一次操作由 `pid` 和 `trace` 关联。每个上传阶段在开始、结束时各记一条;结束记录有 `elapsed_ms`、`status` 和安全的错误码。仅有开始记录时,可直接定位仍在执行的步骤。

| event / stages_ms 字段 | 含义 |
| --- | --- |
| upload_local_flush | 刷新本地暂存缓冲 |
| upload_hash | 摘要准备;含 size_bytes、reused_bytes、pending_bytes |
| upload_create | 创建云端上传 |
| upload_conflict_lookup | 重名后查找已有对象 |
| upload_urls | 获取或刷新分片地址 |
| upload_read_part | 从暂存读取一片;含片号、字节数 |
| upload_put_part | 一次分片 PUT;含片号、尝试次数、字节数 |
| upload_progress | 成功上传的累计片数、累计字节数与总量 |
| upload_complete_wait | 完成接口返回 04010322 后的退避等待 |
| upload_complete | 一次云端完成请求;含尝试次数 |
| upload_wait | 同文件操作等待现有上传;在操作汇总中累计 |

慢 `flush` / `release` 的操作汇总含总耗时、各阶段累计耗时,以及 `hash_reused_bytes`、实际 `hash_read_bytes`、`uploaded_bytes`、PUT/完成请求次数。未出现的计数视为零。分片重试不会重复计入成功上传字节数。阶段嵌套,耗时不能简单相加。日志不含文件名、鉴权、预签名地址、文件/上传 ID、完整摘要或请求/响应正文。

全局锁仅用于建立/发布上传状态、维护句柄和失效缓存;本地刷新、摘要扫描、上传请求、分片读取与退避均在锁外执行。每个 Entry 的 `uploading` 状态阻止同文件写入、截断、重复提交、改名、删除与替换在上传中途修改内容或身份。条件变量等待会释放全局锁;醒来后重新校验句柄或路径。上传中 entry 保持存活,最后一个句柄的关闭与提交发布在同一次锁内清理,防止其他写入被误清脏标记。

属性查询使用暂存对象记录的大小,不会 seek 上传流。并发本地读取使用 `read_at`,在流锁下读取并恢复上传游标;摘要补算和本地读取的等待不占用全局锁。新建本地节点立即带创建/更新时间,避免云端提交前 Windows 查询到 Unix epoch。

新增并发测试先在原实现上复现目录/属性查询超时,修改后通过;覆盖同文件修改等待、其他文件继续写入、重复 flush、并发 release、改名/替换/删除、失败后重试、无句柄 truncate 的间接 release,以及本地读不破坏上传内容。日志测试覆盖 SHA 补算/复用计数、403 地址刷新、04010322 退避、分片进度与敏感信息排除。当前完整单元测试共 56 项。

Windows 挂载验证使用本地 mock 的独立空闲盘符,包含分片提交、Range 读、原生句柄操作与创建时间。T11 的写入和远端地址过期读取分置于重挂前后,确保本地暂存或操作系统缓存命中不会绕过远端地址刷新检查。真实云盘重挂后仍需人工复制大文件验证。关闭文件继续同步等待云端完成;此次改动改善其他文件/目录的响应,不承诺消除复制进度条的最后等待。
