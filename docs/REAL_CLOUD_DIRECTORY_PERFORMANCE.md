# 真实云盘目录打开复测

后续已实施远端读锁拆分和小探测窗口，真实云盘并发读取对比见 [读锁与文件头优化](READ_PROBE_PERFORMANCE.md)。本页保留实施前的诊断记录。

测量日期：2026-11-16。**真实小目录的冷打开没有证实明显加速；仍存在可感知的亚秒级等待。** 普通缓存内重开很快，但冷路径、5 秒缓存过期以及文件读取占用全局锁时，仍可能出现短暂停顿。不能将首轮 3000 项 mock 测试的 89% 加速比例用于当前真实目录。

## 环境与口径

- 从运行中的 Y: 进程确认其使用 `D:\mCloudDownload\ydfs.local.json`，连接中国移动云盘生产服务。项目根目录的同名 JSON 是本机 mock 配置，两个配置没有混用。
- 真实鉴权、HTTPS、原有专用云盘根目录；Windows Python 3.14.3、WinFsp FUSE 3.2。独立挂载只读 X: 网络盘，使用新的共享名称，原有 Y: 进程与窗口保持不动。测试结束卸载 X:，关闭新建的资源管理器窗口。
- 在专用根及已存在的子目录中选取三组：根目录 12 项、一级目录 14 项、两级目录 2 项。没有为扩大样本在云端创建文件。未测试真实千项大目录。
- 优化前使用首轮保存的独立基线副本，保留旧线性扫描和每页 100 项；优化后使用工作区的名称索引和每页 1000 项。保留相同适配器、TTL 和目录阶段日志。核心每组 5 次；实际挂载每组重挂 3 次，均取中位数。
- 使用产品默认元数据 TTL 5 秒；每次核心冷打开清空缓存，测“列目录＋逐项属性”，随后立即重开。挂载使用 `os.scandir + entry.stat`，不计启动时间。每组另在一次挂载中等待 5.2 秒测过期后重开，该指标只有一个样本。
- 校验前后目录内容摘要及挂载列表的名称、类型、大小一致。报告、日志不含凭据、预签名 URL、原始目录名和云端 ID；只保存目标摘要。核心比较工具仅允许 `/file/list`；挂载为只读，没有在云端创建、修改、改名或删除文件。补充争用测试只读取已有文件头，不打印或保存内容。
- 前后顺序测量，非随机交错；网络抖动与小样本影响显著。以下不用于推断 P95/P99。

## 各阶段耗时

优化后核心冷列目录阶段，5 次中位数，毫秒：

| 阶段 | 根目录 | 一级目录 | 两级目录 |
| --- | ---: | ---: | ---: |
| HTTP 等待 | 177.264 | 348.791 | 443.864 |
| JSON 解码 | 0.188 | 0.445 | 0.352 |
| 缓存索引构建 | 0.011 | 0.023 | 0.022 |
| 路径解析，包含祖先请求 | 0.001 | 150.328 | 315.677 |
| 锁等待，纯目录测试 | 0.001 | 0.002 | 0.002 |
| 生成名称 | 0.004 | 0.004 | 0.003 |

阶段相互包含，不能相加。`http_wait` 包含连接、TLS、服务端及传输等待，当前没有进一步拆成 DNS/TCP/TLS 子阶段。网络约占本轮冷列目录耗时的 99% 以上。全冷路径每深入一层，要先解析该层父目录，因此看到 1、2、3 次串行请求。

实际挂载中，优化后的原生 `native_fill` 最大仅 0.041 ms。初次容量请求 `statfs` 在挂载启动期间发生，优化后 9 次记录为 157–215 ms；在挂载就绪后调用容量 API 约 0.7 ms，是缓存命中，并非真实容量接口只需要 0.7 ms。容量与列目录测量分别记录。

## 资源管理器验证与残余卡顿

使用独立只读 X: 盘，在新建资源管理器窗口的“详细信息”视图中检查根目录、进入 14 项子目录、F5 刷新、返回根目录、再次进入子目录。界面最终分别显示正确的 12/14 项，未观察到持续数秒的未响应或错误对话框。自动化工具的输入到截图耗时包含工具和快照开销，且 UIA 文本与截图可能来自不同瞬间，**未将它当成窗口首帧耗时**。

这一段 GUI 测试记录了 438 次 `getattr` 和 8 次原生目录枚举。虽然目录填充很快，仍捕获到：

- 一次属性查询 `total_ms=622.745`，其中 `lock_wait=622.692`。
- 另一次属性查询 `total_ms=532.298`，其中 `lock_wait=532.250`。
- 容量刷新最长约 374 ms；该刷新使用独立容量锁，不将其直接归因于文件系统全局锁等待。
- 部分 `status=error` 是资源管理器探测不存在文件时正常返回 ENOENT，不能单凭该字段判断云端接口失败。

因此，**实际使用仍可能有半秒左右的停顿，不能下“完全无卡顿”的结论**。首次 GUI 日志没有对持锁文件读取分阶段，不能逐次断言上述两次等待的具体持锁调用。

随后补充了 `open`、`read`、容量请求日志，以及 `download_url`、`range_read`、块缓存命中和实际下载字节计数，并用真实云盘执行可控的并发读取：一个线程读取已有最小 EXE 的前 32 字节，确认它进入下载阶段后，另一线程列出已缓存的根目录。仅允许列表、下载取址和预签名 Range GET，不写入云端。

| 样本 | 读请求字节 | 实际下载字节 | 取址 ms | Range ms | 缓存命中的列目录锁等待 ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 32 | 2,725,780 | 105.990 | 124.188 | 230.068 |
| 2 | 32 | 2,725,780 | 92.465 | 126.460 | 218.880 |
| 3 | 32 | 2,725,780 | 93.591 | 99.543 | 193.100 |

这直接证明：默认 4 MiB 读块策略会让很小的文件头请求下载整个 2.6 MiB 文件，并在网络期间持有全局锁；即使目录缓存命中，列目录仍等待网络读取完成。它复现了 GUI 中同一类锁竞争，资源管理器读取图标/属性是合理的触发来源，但不能将首次 GUI 中的每一次等待都反推为同一个调用。

## 后续优化重点

1. 优先让远程文件读取不长时间占用文件系统全局锁。应先在锁内固定句柄/版本和本地状态，在锁外执行取址与 Range 请求，再安全合并缓存；同时验证关闭、删除、改名、写入及缓存失效的并发语义。不能简单移除整个读锁。
2. 为文件头、图标和属性探测评估小范围读取或自适应读块，避免 32 字节请求触发数 MiB 下载；保留顺序大文件读取吞吐，并测请求数和流量的权衡。
3. 冷路径的主要成本仍是远程往返。应测量连接复用与祖先目录缓存命中，分别验证收益；延长 TTL 会影响多端更新可见性，不能只为成绩直接放大 TTL。

本次按“真实复测、对比和确认卡顿”的范围补充诊断，没有修改上述锁与读块行为。名称索引和大分页优化仍保留；真实千项目录的收益尚待有相应只读样本时验证。
